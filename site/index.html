Firecracker sandboxes on Kubernetes.

Every sandbox is a microVM that runs only while it's awake. Idle ones sleep as snapshots in object storage and wake on any node. loam speaks E2B's API, so the official SDKs work against your own cluster unchanged.

Get it on GitHub Read the docs 
# point the E2B SDK at your loam
export E2B_DOMAIN=e2b.loam.example.com
export E2B_API_KEY=loam_...

from e2b import Sandbox

sbx = Sandbox.create()
r = sbx.commands.run("uname -a")
print(r.stdout)   # a Firecracker guest
sbx.pause()       # memory + disk to S3

Same code you'd run against hosted E2B. Only the domain and key change.

How it works

A sandbox is a record in Postgres. Each KVM node runs one warm worker pod, the nodelet, which boots Firecracker VMs inside itself, owns their network, and pauses them to an S3 bucket when they go idle. Waking a sandbox never waits on the Kubernetes scheduler or etcd.

Every state is a snapshot

Pause, checkpoint and fork all write the same layered format, dirty blocks in 2 MiB zstd frames. A paused sandbox costs its diff in the bucket and nothing on the nodes.

Wake anywhere

Wake prefers the node that already has the snapshot and falls back to any node with room. Drain a node and its VMs pause, upload and come back elsewhere with their processes intact.

The network is the boundary

Egress by hostname, checked at DNS and SNI. Secrets swapped in on the wire so they never enter the guest or its snapshot. A per-sandbox OIDC token for identity.

E2B's API, on your cluster

The adapter runs E2B's own envd inside the guest, so commands, files, streaming and signed file URLs behave the way the SDKs expect. Every E2B sandbox is also an ordinary loam sandbox, visible to the loam CLI and API.

Works today

  • Create, get, list, kill, set timeout
  • Commands with streaming, background processes, stdin and PTY
  • Files, plus signed upload and download URLs
  • Pause, resume, connect and auto-resume
  • Sandbox ports at <port>-<id>.<domain>
  • Internet access toggles and hostname egress rules

Not yet

  • Template build API (loam builds templates from OCI images)
  • E2B's snapshot and fork endpoints (loam's own API has both)
  • Volumes, sandbox logs and metrics history
  • CIDR and IP egress rules
  • Team and API key management through E2B's API

Run it

loam needs x86 nodes with KVM, so bare metal or a cloud instance with nested virtualization, on Linux 6.1 or newer. Beyond that it asks for a device plugin that exposes /dev/kvm, /dev/net/tun and /dev/userfaultfd, an XFS directory with reflinks for each node's cache, an S3-compatible bucket and Postgres.

The nodelet runs unprivileged with a short list of added capabilities. The install is a kustomize base with an example overlay; docs/INSTALL.md walks through it, from the device plugin to your first API key.

# a kustomize base, and an overlay of your own
git clone https://github.com/arugula-salad/loam
cd loam/deploy/examples/basic
# set your domain, S3 bucket, Postgres and secrets
kubectl apply -k .

# the native CLI
loam login --url https://api.loam.example.com
loam create dev --template base
loam exec dev -- python3 -V
loam pause dev

loam is young. The API server runs as one replica, and VMs share their nodelet's cgroup. Bug reports welcome.
